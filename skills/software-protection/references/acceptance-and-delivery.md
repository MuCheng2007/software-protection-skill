# 验收与交付

## 按架构选择有意义的用例

| 用例 | 预期观察 |
| --- | --- |
| 有效授权、允许功能与设备 | 真实受保护操作成功，结果与原程序一致 |
| 修改签名载荷、错误公钥/产品/算法、格式畸形 | 明确拒绝；不覆盖有效缓存、不崩溃、不泄漏 secret |
| 未生效、到期边界、永久授权 | 按已定义 UTC 语义处理；缺失或异常字段不意外放行 |
| 复制许可证到另一设备 | 按设备策略拒绝或走恢复流程；不夸大抗克隆能力 |
| 调整本地时间、恢复旧缓存 | 记录已观测行为与仍可绕过的边界 |
| 断网、超时、TLS/服务故障 | 按离线窗口和失败策略处理；没有无限隐式宽限 |
| 撤销、旧租约重放、换机和注销 | 满足已承诺的生效延迟和席位回收语义 |
| 同时激活最后一个席位、请求重试 | 不超售席位，不重复创建授权，不误占额外席位 |
| 跳过 UI，通过 CLI/插件/直接 API 执行 | 对需要保护的路径实际执行授权检查 |
| 公钥轮换、服务迁移、版本升级与回滚 | 合法用户按迁移策略继续使用；不能通过降级恢复已禁权限 |
| 最终分发包检查 | 没有签发私钥、管理凭据、测试后门及意外发布资源 |
| 恢复、导出及授权错误展示 | 用户数据完整，可理解错误并恢复正常使用 |
| 自部署服务授权模块被测试替换、客户端上报原始文件摘要 | 记录真正仍受提供方控制的能力；不把正确摘要当作正在执行原代码的证明 |
| 未来时间戳、去重过期、同nonce并发和错误签名 | 不在请求仍有效时丢失去重记录；原子拒绝重复，错误认证不消费正常请求的nonce |
| 断网冷启动、多网卡和顺序变化、禁用/更换网卡 | 按设备政策稳定识别并提供恢复；不因网络状态误拒合法离线用户 |

有源码时运行与改动相关的集成/行为测试及构建检查；只对适用项设计测试。涉及二进制改造时还需比较原件摘要、重建/签名结果、启动和关键功能回归。没有二进制就不要声称已验证抗逆向能力。不要把仅检查文件存在或关键词匹配当作行为验收。

如做篡改验证，只操作授权的隔离副本和测试服务，测试目的是验证自己的保护边界；保持用户数据与正常服务可恢复。不得把“本轮未绕过”等同于安全证明。

## 完整方案的输出

按项目规模组织，避免用空泛清单代替结论。至少包含：

1. 目标与假设：程序形态、可用材料、攻击者能力、联网约束、商业授权规则，以及关键待确认信息。
2. 保护重点：按风险排序的实际位置、证据、影响、修复措施和验收方式。无项目时明确这是参考模型。
3. 推荐架构：本地/联网/混合选择理由、信任边界、端到端流程及关键能力保留在哪一侧。
4. 接入设计：明确校验点、许可证/租约结构、接口语义、凭据与密钥流向、设备/席位规则、异常状态和用户恢复方式。可用 Mermaid 表示流程。
5. 实施顺序：先修复高权限秘密泄漏与服务端控制缺失，再建立可靠授权链，最后按收益增加逆向成本；给出依赖、工作量区间及依据，不虚构精确报价。
6. 运维与迁移：发卡、续期、撤销、换机、轮换、备份、故障和旧用户迁移；区分开发示例、测试环境与生产部署。
7. 验证与限制：已执行用例和结果、未执行用例、外部依赖、剩余风险与上线所需条件。

涉及核心算法或客户端完全失陷目标时，补充 [hostile-client-design.md](hostile-client-design.md) 中的设计结论、关键计算拆分与直接 API 验收。对“云端下发即可安全”等现有方案明确判断是否达到目标，解释已下发材料、离线使用和撤销承诺之间的冲突。

若实施了代码，再列实际文件改动、构建/运行方式、配置项和回滚方法。真实密钥不进入交付文档；给出注入位置和占位配置。只提供方案时，明确没有修改或部署目标程序。

## 用于检查 skill 行为的场景

这些是评估输入，不是已经跑过的测试结果。根据新案例还应覆盖：

- 用户说“RSA 改成 Ed25519 就能防住参数篡改吗”：应区分算法伪造与本地执行链修改，不承诺换算法即可修复。
- 用户说“加了 20 处校验”：应追踪是否共享一个可改授权结果，不把数量当作独立信任边界。
- Electron 仅验证归档摘要、外置组件可写：应检查实际加载对象、搜索路径、更新和恢复链，而非只建议重新计算哈希。
- 用户给论坛列表上“昨天”的旧帖：应核对正文发布日期；设想教程不能计为商业软件实际破解。
- 网络租约有签名但设备上可替换公钥：应审查信任锚，并解释客户端控制局限；服务端继续根据自身记录授权关键操作。
- 后台 UI 不让改 secret：应验证服务端字段限制和租户权限，不因 HTTP POST 可见就直接断言后台未鉴权。
- 用户说注册流程已验签，但重启只读本地已注册标记：应覆盖启动恢复、导入和旧版迁移路径，不能只测试激活窗口。
- 用户说“RSA 128位也用了非对称加密”：应核对实际参数，区分RSA模数位数和对称安全强度，给出迁移方案；不能把参数升级当成抗本地篡改保证。
- xlsm通过CPU、MAC和机构名绑定并联网取时间：应检查移除授权调用后业务是否仍可运行，区分普通网站时间与授权服务受信时间。
- 公钥存在外置模块或配置中：应测试替换公钥后另一密钥签发的凭据是否被接受，同时测试合法轮换；不能把公钥可见直接报告为秘密泄漏。
- 论坛建议“本地HMAC加网络返回值即可彻底解决”：应重新分析真实业务的执行位置，拒绝把局部示例变成无条件保证。

- 用户没有代码，只问“给 Python EXE 加永久离线授权”：应交付带假设的参考设计，说明签名与本地执行边界，不虚构反编译发现。
- 用户有 Electron 源码，已有联网验证返回 `true`，要求“防 REA”：应检查服务端执行边界与客户端 secret，不把混淆或隐藏 URL 当成核心访问控制。
- 用户要求七天离线，同时要求撤销一分钟内生效：应指出完全离线时这两个要求不可同时保证，给出可选择的取舍，不承诺两全。
- 用户要自建、无预算、不能联网：应采用离线签发路线讨论限制，不强行引入托管服务。
- 用户只有签名 EXE、没有构建环境，要求一键包一层：应解释外壳的直接启动绕过与签名影响，给出可行分阶段方案，不冒充已实现程序内保护。

实施项目还可从 failure-patterns.md 选用受信公钥/验签结果替换、跨租户响应、实际加载文件替换等测试；所有测试只针对自有授权副本。记录具体执行方法与观测，区分测试接缝模拟和正式产物篡改验证。
