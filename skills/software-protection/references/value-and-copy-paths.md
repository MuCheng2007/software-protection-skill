# 产品价值、复制路径与保护落地

用于核心算法、资源、模型和产品能力保护。与授权执行分别评价；按实际项目选择检查项。

## 核心思想

先回答“别人复制这个产品的价值，最便宜的路线是什么”，再回答“授权怎么加”。同时评估跳过授权、直接调用业务接口、提取算法/模型/资源、观察输入输出重写，以及利用已有开源实现替代。以用户真正希望保住的资产排序，不能默认把所有预算花在本地校验上。

授权执行、实现保密、资源分发控制、抑制接口滥用和增加重建成本分别给结论。无法靠技术保证的目标，应说明边界并提供可选取舍，不用“上云”“原生化”“加壳”代替方案。

## 一、先理解项目，再选技术

优先读取真实项目与最终产物：

| 类型 | 需要检查的配置与材料 | 需要进一步确认 |
| --- | --- | --- |
| Python | pyproject.toml、依赖锁、入口、PyInstaller spec/Nuitka命令、扩展模块、发布目录 | 核心是Python计算、原生库调用，还是模型/资源；动态导入与部署约束 |
| Electron/前端 | package.json、构建配置、preload/IPC、主/渲染进程、归档、source map | 算法实际在哪执行，是否依赖可直接调用的本地/远端接口 |
| .NET/Java | csproj/构建属性、Gradle/Maven、程序集/JAR、反射、序列化与插件 | 混淆与裁剪是否破坏动态行为；哪些模块适合原生化或服务化 |
| C/C++/Rust | CMake、vcxproj、Cargo、编译器/链接器版本、优化与LTO、map/符号、目标架构 | 源码级混淆和产物级保护的兼容性、边界与回溯能力 |
| Android/iOS | ABI、Gradle/Xcode、签名、JNI/原生库、网络与更新路径 | 目标保护工具实际支持的平台与指令集，商店分发及合法设备兼容 |
| 模型/素材/规则产品 | 权重、词库、模板、规则表、压缩包、缓存、更新清单 | 资源是否本身承载主要价值，下发后能否独立复用 |

未确定的架构、编译器、位数、发布方式应标为未知；同一个语言不能套同一份处方。没有源码时只给可核对的产物级建议与接入前提。

## 二、主动确认工具与约束

从配置可得的内容不重复问；未能确定、且影响方案时主动问：

- 目前有没有使用或持有 VMProtect、商业混淆器、编译器混淆方案或硬件保护工具？版本、授权版本、SDK、目标平台及工程配置能否提供？
- 是否允许将核心模块改为 C++/Rust 扩展？是否具备维护、构建与跨平台发布条件？
- 是否必须离线，是否能部署提供方控制的服务？可接受多少启动/运行开销与运维预算？

不要求用户先购买工具才能得到方案。给出已有工具接入路线、低预算路线和需要另行采购/验证的选项。不默认下载、执行商业工具，不擅自更改许可证或构建环境。

## 三、建立最短复制路径表

每条路径记录资产、真实文件/符号/资源、可得证据、攻击前提、复制或替代步骤的概括、可得到的业务价值，以及影响、成本区间与估算依据。不要编造精确破解时长。

特别测试：不使用原程序的授权模块，单独拿出算法/模型/资源后是否仍有价值？不拿出实现，只通过合法输入输出是否容易复刻？现成公开实现是否已能替代？

根据最便宜路径排序。例如：主价值在完整权重文件时，先评估权重分发；核心是公开算法时，先确认真正差异是否在数据或工程；核心只有几十行规则时，混淆成本可能超过重写成本。

## 四、给出项目适配的具体路线

| 情形 | 应提出的候选方案 | 必须说明的代价与限制 |
| --- | --- | --- |
| Python中可独立复用的高价值计算 | 提取输入输出明确的核心模块；评估C++/Rust重写、Cython或合适的编译路线；在适用原生产物上评估局部混淆/虚拟化 | 类型、异常、数值精度与ABI回归；跨平台轮子和工具链维护；不是把全部UI重写 |
| Python主要调用已有原生推理/数学库 | 优先检查权重、参数、规则与调用接口；避免只改写薄封装 | C++封装不会让公开库或完整权重自动保密 |
| Electron中有价值的本地JS算法 | 检查IPC和实际消费点；评估核心原生模块或服务端计算；约束调用输入与权限 | 搬到主进程、WASM或原生层不是保密证明；导出接口仍可能被独立调用 |
| .NET/Java逻辑易读 | 按反射/序列化约束选择混淆范围；必要时局部原生实现或服务化 | 不强制全项目迁移；验证插件、AOT及动态加载兼容 |
| 原生程序 | 按函数价值与性能特征选择编译混淆、虚拟化、发布完整性与诊断策略 | Rust不自动防逆向；保护热点可能严重拖慢；已有二进制不能直接套源码级LLVM pass |
| 高价值权重、词库、模板和素材 | 最小化下发，评估按需分发、提供方服务端执行、版本/客户水印与泄漏追踪 | 本地要完整使用的明文可能被复制；水印便于归属分析，不是访问控制 |
| 观察功能就能重写 | 缩小必要接口输出，控制已授权批量查询，保留持续更新数据/服务的价值 | 限流不消除慢速仿制；不靠恶意错误结果或损害正常用户来制造“安全” |

用户举例的合理推荐应具体到：“将某文件中的某核心计算抽到原生模块，Python保留UI和编排；对原生模块中少量高价值、能承受开销的函数评估适配的OLLVM方案或VMP，再验证结果和性能”。若原生函数只是返回一个可替换布尔值，而全部业务仍在Python，应明确指出它没有达到目标。

C++重写不是默认答案：先评估能否达到保护收益、是否被公开等价实现轻易替代，和是否值得新增维护负担。

## 五、必须交付保护位置，而非工具名称清单

源码可用时，每个候选至少列出：真实路径和符号、资产、拟保护范围、选用机制、保护前置条件、构建产物、预期收益、性能预算、回归测试和剩余风险。

优先候选：专有规则评估、关键转换、核心计划/评分计算等有商业价值的真实业务实现。根据调用频率选取较小且可封闭的区域；检查跨区控制流、异常、提前返回、内联/LTO和函数边界，不盲目框整个程序。

通常不值得重保护：界面绘制、日志、网络等待、通用依赖、极高频循环；但是否排除应由项目测量决定。签发私钥不因被标记保护而允许放进客户端。

VMP等SDK标记只用于声明拟保护区域，仍需要实际保护步骤。下面只是原生模块的接入示意，不对应已检查项目：

```cpp
// 示意：API、包含文件与支持情况以用户实际SDK为准。
Output run_core(const Input& input) {
    // 先准备输入及可跨边界的状态。
    VMProtectBeginVirtualization("core_compute");
    Output result = proprietary_compute(input);
    VMProtectEnd();
    return result;
}
```

这个示意仅表明调用处的区域：被调函数的主体不一定因此受保护。若秘密在 proprietary_compute 内，要按工具支持显式选择它或在其合适区域放置标记，并在最终产物中确认实际覆盖。不能只保护调用壳或导出包装器就说整个调用图已被保护。处理区域内异常及提前退出时，以实际工具限制和测试为准。

OLLVM类方案在编译/中间表示阶段工作，应落实到选定编译单元、函数与工具支持的配置；没有通用的VMP式标记API。核对所用分支、LLVM/Clang版本、目标ABI与构建系统，不把旧项目的命令行照搬到现代编译器。

发布方案说明：明确每步处理的输入产物、工具版本/工程配置和输出产物；根据工具要求安排编译、局部保护、打包及最终签名/完整性步骤。测试的是最后实际分发的包，而不是只检查SDK导入或源码标记。

## 六、指出不合理设计，并给替代方案

- 核心算法必须保密，却完整留在可检查的脚本层，仅反复改名或加密源码：评估局部原生化/服务化及其接口，不继续无效堆叠。
- 壳很复杂，但权重/规则/素材直接可复用：先处理资源分发与消费路径。
- 加固DLL只负责验卡，业务完全独立：检查移除它后还能得到什么能力，不能只增加调用次数。
- 云端给固定常数就认为本地失守也不能用：做一次合法运行后的材料复用测试。
- 全函数/全程序最高强度保护：按性能和可维护性缩小重点；多个工具不默认叠加，先验证组合兼容与增量收益。
- 把公开算法或可低成本重做的功能当独有秘密：说明保护收益有限，考虑预算投入数据质量、更新和服务。

## 七、给投入取舍和验收

对重点资产提供基础、局部迁移、服务/硬件三类适用选项，不机械凑齐三档。比较实现与长期维护、许可证、性能、兼容性、故障恢复、用户体验和复制成本提升；用户已选方案优先。给推荐、暂缓项与不建议项及理由，不承诺不可复制。

实施级验收至少选择适用项：保护前后算法一致性和边界输入；导出接口是否能独立复用；资源在解密/推理/渲染时是否暴露；删除授权后新业务是否可做；黑盒输入输出能否轻易拟合；最终原生产物保护覆盖；启动/运行性能、异常恢复、更新签名与合法用户兼容。未实际执行的验收写成计划。

## 依据及边界

- VMProtect官方手册：https://vmpsoft.com/vmprotect/user-manual/ 。标记是保护区间标签，需要后处理；实际SDK/平台与控制流支持按用户版本核对。
- 原始OLLVM仓库：https://github.com/obfuscator-llvm/obfuscator 。其公开说明标识LLVM 4.0，不代表所有现代LLVM分支的能力或兼容性。
- Nuitka官方手册：https://nuitka.net/user-documentation/user-manual.html 。编译、扩展模块、依赖和分发方式应查实际配置；不能将编译或单文件分发当作保密保证。

没有目标源码时只给明确假设的参考位置；没有执行时，不声称完成原生迁移、保护覆盖或抗逆向验证。
