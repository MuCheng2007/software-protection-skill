# 授权与保护失效模式

这些是审查维度，不是所有程序都已存在的漏洞。公开案例仅提供检查线索；防护和测试是本 skill 的工程建议。案例 ID 可在 forum-cases.json 核对。对每个适用模式交付：资产/位置 → 项目证据 → 攻击者前提 → 最小改进 → 验收 → 剩余风险。没有项目证据写“待确认”。

## F01 密码算法正确，但执行链可被修改

线索 C01、C02、C09、C19。检查信任公钥及其加载来源、算法/参数、验签返回值、声明解析、完整性检查的取数路径和授权后的执行边界。不能只检查“是否用了 RSA/Ed25519”。公钥可以公开，问题是攻击者能否替换其信任来源；隐藏公钥不是密码学要求。

控制：固定受信 key_id 与算法映射，采用标准验签 API 并验证编码及业务声明，防止许可证自带任意信任锚；检查验签失败后所有执行路径。评估运行时篡改成本，以及能否把真正的能力放在受控服务或隔离硬件中。参数自检、双重验签与混淆只能作为本地加固，若共享同一个可篡改信任根，不能声称它们独立可信。

验收：在自有隔离测试副本中，分别模拟受信公钥替换、密码结果替换、关键参数变化、声明解析结果被替换和完整性读取返回旧内容；观察真实功能是否仍受约束。单独覆盖外置公钥/证书、native模块与授权配置的替换组合，检查另一测试密钥签发的许可证是否被接受。可先用故障注入/测试接缝检验行为，但它不等于证明正式包能抵抗同样的修改。RSA 指数被改成 1 是特定示例，不意味着更换签名算法即可消除客户端篡改风险。

## F02 伪造服务或改配置后，客户端接受另一个授权体系

线索 C04，C05 仅为设想示例。检查 endpoint、product/tenant ID、软件共享 secret、验签公钥是否集中在可替换配置，是否接受跨产品/租户签发的租约，以及响应签名是否真正执行校验。

控制：标准 TLS 校验，签名响应绑定发行者、受众、产品、设备、权限和有效期；公钥信任来源与普通配置分离。客户端内共享 secret 不承担证明“官方签发”的唯一责任。服务端按真实账户/租户与授权记录执行受保护操作，而非只下发本地解锁标记。

验收：测试环境返回成功状态但没有有效签名、替换发行者/产品/设备、接入第二个测试租户或旧服务、重放旧租约；正式业务服务仍应拒绝未经授权的操作。更换 URL、加密 JSON 或隐藏接口不能代替这个边界。不能因 HTTPS 可在受控设备上被观察就声称 TLS 被破解。

## F03 客户端校验规则足以重建发卡能力

历史线索 C08；C06、C17 为教学样例。检查授权是否仅依赖 CRC、可逆编码、散列拼接、资源隐写、客户端共享密钥和可重建规则。CRC/哈希可用于检错，不代表签发方身份。

控制：将发卡能力放在独立签发端，客户端只具备公钥验证能力；或由服务端维护授权。不要仅增加更多字段、黑名单或改用更长哈希来修复缺少签发方认证的问题。

验收：确认发布包及可访问配置不足以独立签发新许可证；修改产品、功能和期限必须使签名验证失败。纯本地算法加密/编译只能增加分析成本。

## F04 字节码、ASAR、资源或压缩壳被当成保密边界

线索 C02、C03、C06、C08、C17。清点脚本、V8/托管字节码、Python 包、native 模块、资源文件和解包缓存；检查是否包含签发凭据或可直接复制的高价值资产。不要把界面无明文、文件扩展名或“AI 读不懂”当作秘密不可提取的证据。

控制：先减少下发资产和高权限秘密，再选择适量混淆/编译；保留可诊断的私有符号。发布包清理日志、源码映射和测试开关，不能为隐藏授权而破坏用户需要的正常错误信息。授权码、token、完整设备指纹及解密后载荷也检查日志、崩溃转储和诊断包；不要默认短字符串前缀或无盐哈希足够脱敏，低熵内容仍可能被推测。

验收：检查最终包而非仅源码；用可用只读工具抽取目录/资源并评估暴露面。格式无法直接读取只表示工具能力不足，不证明安全。

## F05 完整性只验下载包，实际加载文件或更新入口仍可被替换

线索 C03 是组件修改案例，不是付费授权破解。检查验证覆盖的对象与真实加载对象是否一致；manifest、归档、解包目录、动态插件、缓存、seed 与 OTA 各路径是否同样受控。哈希值和文件一起被攻击者修改时，哈希不构成真实性证明。

控制：受信签名清单覆盖实际执行资产，验证与加载尽量绑定，使用原子更新和受限写入目录。防止验证之后、使用之前文件被替换；需要时通过受验证内容句柄或等效机制缩小窗口。更新与恢复路径也验证来源、版本和通道，允许经过授权的可靠回滚。

Electron 项目按当前官方文档及目标版本评估 ASAR integrity 与 OnlyLoadAppFromAsar 配套启用，关闭不用的 RunAsNode、NODE_OPTIONS 与 inspector 能力。先测试子进程、诊断和更新兼容性，再在代码签名前配置 fuses。代码签名是否阻止被改程序运行取决于实际 OS 策略；不能把签名存在当作所有设备强制校验。

官方依据：https://www.electronjs.org/docs/latest/tutorial/asar-integrity 和 https://www.electronjs.org/docs/latest/tutorial/fuses 。这些功能增加完整性保障，不等同于阻止设备所有者修改整个运行环境。

验收：分别修改归档、已解包执行文件、manifest、加载搜索路径与旧版本资源；覆盖首次启动、升级、换通道、恢复和自动更新。验证失败保留用户数据并提供修复入口。

## F06 看似多个校验点，实际都依赖同一个可写状态

线索 C01、C02、C09 提示共享瓶颈。追踪授权状态的生产与消费，检查 UI、CLI、插件、导出和后台任务是否共享一个可替换返回值或单一解锁因子。增加调用次数不自动增加独立性。

控制：统一业务规则防止漂移，在真正付费操作边界执行授权；服务端资源由服务端判断。区分复用规则与所有保护依赖同一客户端布尔值。必须本地执行时描述成本提升，不能虚称已建立不可绕过边界。

验收：授权结果被模拟为成功时，检查是否能访问未授权服务端资源；取消/过期后测试所有付费入口与已启动长任务。

## F07 授权后台把界面限制当成 API 权限与字段约束

线索 C04。“请求是明文 POST”本身不证明无权限校验；作者未测试的越权推测不能当作已确认漏洞。应核对实际身份鉴别、租户归属、可修改字段和秘密的生成策略。

控制：服务端重新校验对象归属、字段白名单、状态转换及密钥管理策略；客户端可见的 product ID 是标识符，不是管理权限。发卡/撤销/密钥轮换单独鉴权及审计。若设计规定密钥由服务端生成，不能仅依赖后台 UI 禁止编辑。

验收：自建测试环境用低权限及另一租户凭据请求修改产品、密钥或许可证，确保拒绝且状态未变；检查日志不输出密钥。不要针对未授权第三方后台验证猜测。

## F08 试用、心跳、席位与时间只在本地维护

这是生命周期回归维度。C27短帖声称阻断心跳后继续运行、恢复通信后失效，但缺少版本与完整测试条件；C28涉及旧软件时间检查，C42原文代码只用本地时分和时间窗判定短授权码。这些提供测试线索，不证明流行程度，也不证明所有心跳系统都能绕过。

控制：服务端以受控时间与原子状态管理席位/续租；本地宽限有期限。区分“服务器能发现租约未续”与“被改的离线客户端会停止执行”；删缓存、重装、快照恢复和设备克隆都纳入威胁模型。

验收：并发占最后一个席位、重复激活、旧租约复用、断网跨过最大窗口、回拨时钟、恢复快照；同时验证合法换机/故障恢复不丢数据。长期离线与即时撤销存在不可消除的取舍。

## F09 注册时校验，但启动恢复/迁移路径直接信任缓存

历史线索 C16。区别用户偏好数据、授权凭据与已经验证的运行状态。检查首次激活之外的启动、自动登录、导入备份、旧版本迁移、离线启动和恢复流程；本地文件/注册表/plist 里的 isRegistered、期限和权限字段不能直接成为权威授权。

控制：恢复时重新验证签名许可证/租约及产品、设备、有效期等声明，只从验证结果建立运行权限。缓存只保存凭据及辅助信息；删缓存或格式错误不能进入默认已授权状态。OS 安全存储用于提高窃取/修改成本，不等于抵抗控制该用户运行环境的人。文件没有加密不必然有漏洞，关键是真实性及使用前验证。

验收：以无效授权直接写入本地状态，重启、导入备份、迁移旧配置、离线启动和跨设备复制，观察付费功能是否仍拒绝。保留正常合法用户迁移和数据恢复。不要将返回界面显示“已激活”当作所有付费功能实际可用的证据。

## F10 密码参数太弱或误把算法名称当成安全强度

历史线索 C16。单独检查实际公钥位数、算法/填充、密钥生成、随机源和库版本，不从字符串名字“RSA”“AES”判断强度，也不混淆 RSA 模数位数与对称安全强度。这与 F01 的运行时篡改属于不同问题。

控制：使用当前官方标准和成熟库的签名方案及合适密钥强度，拒绝测试或异常短密钥，保留升级迁移。若 RSA 必须使用，OWASP 的通用最低建议是2048位；具体长期寿命、合规和签名参数再查适用规范。不要把加密用 OAEP 当作签名方案，也不要照搬论坛的分解耗时表或“统一必须3072位”等泛化结论。

依据：https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html 。许可证生成和运行验证都应约束允许的 key_id、算法及密钥规格，避免兼容旧弱密钥的静默降级。已暴露或被攻破的旧签发密钥需要撤换；单纯升级库不会使旧许可证自动失效。

验收：检查正式构建实际公钥参数与签发配置一致；异常短密钥、非预期算法和失效 key_id 被拒绝；新旧用户迁移与可信回滚按政策工作。提高密钥强度修复密码参数问题，不能保证客户端校验器无法被修改。

## F11 Office/VBA/脚本项目可编辑，授权模块被移除后业务仍独立可用

线索 C18 是作者自述的软件修改说明，细节不足以复现，不能认定它攻破了服务器；C17 为教学补充。检查 xlsm/xlam、VBA、脚本入口、按钮绑定、自动执行事件、公式与本地数据之间的依赖。CPU、MAC、组织名等绑定数量不解决“直接删掉调用者”的问题。

控制：区分文件打开加密、工作表/工作簿保护、VBA项目锁和数字签名各自的作用；工作表保护不构成保密或商业授权边界。宏签名配合可信发布者和可管理的执行策略，可用于受控环境的完整性管理，不等于在用户自管电脑上强制禁止修改。签发秘密不放在宏中。

需要强制保护时，把有价值的运算、数据获取或结果生成放在必须鉴权的服务端，授权检查与真实业务同侧。只将“是否允许”移到服务端，业务仍全部本地执行，不能解决删授权模块。受限联网时可评估签名离线凭据与原生组件以增加修改成本，但明确可被本地篡改的边界，不强迫用户更换产品形态。

不能用普通网站响应时间或 Date 头替代专门的授权时间信任源；联网状态、时间校准、授权状态分别处理，离线宽限写明期限。加密保护用户文档的密钥与商业授权分离，授权失败不能导致用户数据无法恢复。

验收：在自有测试副本中模拟未触发 Workbook_Open、移除授权调用、直接执行业务入口、修改绑定输入与本地授权配置、离线启动；观察业务实际结果。受控签名策略与普通用户可改变策略的环境分别测试。离线且完整业务已下发时，应报告成本控制而非绝对阻断。

官方对保护层次的说明：https://support.microsoft.com/en-us/excel/protection-and-security-in-excel 。具体 Office 策略与平台支持应按当前部署版本验证，不能从“支持签名”推导“所有终端强制验签”。

## F12 混淆或虚拟化提高分析成本，但语义仍可恢复

线索C41、C51、C52、C53、C55分别涉及教学约束求解、函数级lifting、有限轨迹恢复、教学脱壳和特定混淆化简；C37仅有来源作者对SDK标记未实际保护的报告。工具说明、单个纯函数实验与完整商业产品不是同一证据等级。VM区域识别不等于反虚拟化，也不能从个别研究推断所有保护已失效。

检查：最终产物是否实际经过预期保护流程，SDK标记、构建脚本与发布配置是否匹配；有价值的运算、输入和完整依赖是否全部在客户端，授权是否仍收敛到可求解的小型约束或共享本地结果。只从可用工具结果描述当前可恢复部分，不以“工具打不开”推断安全。

静态IAT尚未解析、出现SDK标记或函数能反编译，都不能单独判定保护是否实际应用；需结合最终产物、加载/解析时机和构建证据。不要把“原生层只返回布尔值”直接当漏洞，先查内部验证与真实能力依赖。

控制：优先减少下发的签发秘密和不必本地执行的能力，再针对有价值的局部逻辑选择混淆或虚拟化。保留构建可追溯性、性能预算、私有诊断信息与迁移方案。不要通过加入随机循环、故意崩溃或宣称对抗AI的字符串来替代授权边界。

验收：在自有测试产物中核对保护前后目标函数及实际发布包；按可用工具检查字符串、模块、运行时结果和函数语义暴露，并记录覆盖到的路径和未恢复部分。保护后的合法功能、耗时、崩溃恢复和更新也须回归。只有工具安装、静态不可读或求解一次失败，都不能证明防护通过。

## 导入研究的证据边界

C21提示验签后结果消费点仍需审查，且原文的RSA签名规格存在内部矛盾。C24所列实际模数为108 bit，不能把大整数存储容量当作密钥强度。C25是可重算的客户端发卡规则，不是哈希数学逆转。C26、C47是架构分析，不是成功破解。C35、C36排除出具体失效证据；C49未证明有效证明token可被伪造或通过后端验证。处理安全证明时区分客户端采集链、可信签发、请求绑定、后端验证与最终业务决策，不能从前一层可观察推断后一层已失效。

授权码服务另按F07核对不可预测性、有效空间、速率限制、失败响应与账户/设备/激活绑定；C46仅有响应分类主张，没有完整业务成功验证。验收用自建测试码和受控请求速率，确认无效码、过期码、已用码与并发激活均按政策处理；不对第三方接口做枚举。

## 输出优先级

本轮新增线索按证据使用：C57为自部署Java系统教学，C60为作者本地修改报告，C62为AI辅助重建的局部作者主张，C70报告首处修改后仍未注册，C72的适用版本受到回复反证；均不证明当前产品普遍失守。C65/C66仅支持虚拟化成本与版本差异审查。C71提示可替代配置与关键云端能力的区别。C61为设备授权可靠性故障，无破解模式映射；C56/C58/C63/C64不用于新增具体破解机制。完整处置见各条记录。

优先修复批量签发能力泄漏、服务端越权及跨租户问题，其次修复授权链和发布链，最后增加本地逆向成本。按项目影响调整，不按论坛热度排序。每项明确它属于：预防伪造、服务端强制、完整性保障、提高分析成本或检测/恢复；不可把最后两类写成绝对阻断。
