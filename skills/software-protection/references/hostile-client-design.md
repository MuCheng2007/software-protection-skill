# 客户端完全失陷时的架构审查

适用于“防 AI 逆向”“核心算法保护”“云端下发关键常数/密钥”“本地攻破后仍不能免费使用”的请求。先区分四个目标：提高理解代码的成本、防止伪造授权、控制未来业务执行、减少算法或数据泄漏。一个措施通常不能同时完成四个目标。

## 先检验安全目标是否成立

把客户端源码、内存、磁盘、普通时钟、网络调用代码和授权分支都视为攻击者可控。AI 可以降低分析成本，不会让客户端成为新的可信执行边界。没有针对具体产物的测试，不评价某个 AI 工具一定能破解或一定防得住。

“后端”按控制权判断，不按进程名判断：客户自行部署、可改JAR/容器/数据库的服务仍在其控制范围内（C57提供教学线索）。只有关键能力由提供方控制的执行环境承载，并对实际业务执行授权，才适合称为这里的可信服务端。客户必须完全私有部署时，给出相应本地成本控制、受控硬件或合同/维护权益方案及限制，不假称联网就已解决。

普通客户端上报正确class/模块哈希并非远程执行证明：可提交预期值、读取原始副本而执行修改代码，或改变哈希采集路径。单独检查上报值、将校验迁入JNI、把预期哈希存在云端，都不能保证受控终端正在执行原版代码。若考虑远程证明，必须明确可信根、测量覆盖、请求/会话绑定与验证方策略，不能用自报摘要冒充硬件证明。

把“无法运行”改写成可验证目标，例如：“没有当前有效授权的调用方，无法让服务端对新的输入完成付费计算。”攻击者仍可能启动或修改本地界面，缓存旧输出，或仿制功能。区分无授权者、曾经合法但已撤销者、仍有有效授权但恶意调用者；后者可能用正常接口批量提取结果或转售服务。

必须追问到实际业务依赖：缺失云端数据后，攻击者能否用旧值、固定值、公开数据或替代算法得到仍有商业价值的结果？不要仅凭业务代码引用了某个变量，就认定它构成保护边界。

| 方案 | 客户端失陷后仍能保护什么 | 需要批判的条件 |
| --- | --- | --- |
| 云端返回 `valid=true` | 后端自身可拒绝未授权访问 | 本地逻辑仍可能跳过判断；不是云端执行 |
| 云端下发固定常数、模型或解密密钥 | 首次分发可设门槛 | 合法运行一次后可能提取并复用；短有效期无法让已复制明文自动失效 |
| 云端下发每次不同的数据 | 尚未下发的新数据可能受控 | 判断数据是否真正依赖当前任务；轮换随机值、nonce 或加密传输本身不能阻止重放旧业务结果 |
| 云函数/后端执行关键步骤 | 可拒绝未来未授权的服务端计算 | 函数必须不可被可用的本地替代绕开；每次调用有授权、配额和对象权限检查 |
| 完整核心算法留在服务端 | 减少客户端直接提取实现 | 输入输出仍可能泄漏规律；有权限账号仍可滥用；需评估模型提取、仿制与数据隐私 |
| 纯离线签名许可与本地加固 | 防止直接修改声明、提高分析与修改成本 | 完全控制普通客户端时，不能保证始终执行许可校验或保守核心算法秘密 |

硬件安全模块、TPM、加密狗、可信执行环境或远程证明只在部署条件合适时作为候选。说明其具体信任根、可保护的操作、宿主控制能力、平台兼容及运维成本，不把“用了硬件/证明”当作软件全链路安全证明。

## 为真实项目选择关键计算边界

先列出核心算法/模型/规则及调用者，再找最小但不可替代的服务端步骤。对每个候选给出：输入、输出、为何本地无法从已有材料等价计算、可缓存多久、结果是否可跨用户/任务复用、泄漏后的影响。无法证明不可替代时，明确标为假设，并给出验证方法。静态常数只是商业数据时可以受控分发，但不要包装成持久防破解机制。

比较完整服务化、拆分关键步骤、混合租约和纯离线方案，推荐一个并说明依据。考虑延迟、峰值并发、单次成本、数据出境/保密要求、长期断网、服务停运与合法用户恢复。只迁移与保护目标相关的能力，不为增加网络依赖而把无关本地功能云化。

核心算法必须离线时，说明代码和运行数据最终需要在本地使用，编译、混淆、虚拟化、模块拆分只能增加成本；可结合分客户水印、版本差异和泄漏追踪，但不把水印当作访问控制。服务端不下发核心算法时也不等于算法思想不会被独立实现。

## 云端关键计算的接入蓝图

以下是自建接口的设计示例，路径和字段需按项目调整，不代表任何厂商 API：

1. 激活：`POST /activations` 提交卡密和设备注册材料，后端核对产品、订单、到期与席位，原子登记后签发权限受限的设备/会话凭据。卡密不随每个计算请求传递，不写入 URL 或日志。
2. 提交任务：`POST /jobs` 携带会话凭据、任务输入和幂等键。后端验证身份，读取权威授权状态，检查租户、功能、对象归属、配额和输入边界。不能信任客户端声称的 `paid`、设备归属或功能等级。
3. 执行：后端持有算法、模型或不可替代的数据并计算，不把长期密钥或完整秘密计算材料返回客户端。对排队任务定义撤销生效点；如承诺执行时撤销生效，则执行前再次核验，不能只在入队时检查。
4. 取结果：`GET /jobs/{id}` 再查调用者与任务归属及结果读取策略。结果记录绑定服务端确定的租户、任务、输入摘要和算法版本；跨用户复用受权限控制。若客户端需验证离线结果，签名可证明来源，但客户端被修改后仍能跳过验签。
5. 撤销与退出：停止新计算、使适用凭据失效并处理待执行任务。明确已下载输出、明文资源及先前合法缓存无法被可靠远程收回。短 token 若不查询撤销状态，撤销延迟仍受其有效期约束。

在数据库中至少设计授权、设备/席位、会话或撤销版本、任务和用量记录的关系与一致性；按实际规模选择组件。扣费/配额与任务幂等协调，防止重试重复扣费或并发超额。区分网络重试、业务拒绝和结果未知，明确如何查询已提交任务。

保护 API 还需限制正常授权者的滥用：按账号/设备/租户设置可解释的并发、速率与预算，必要时异常告警和人工复核。设备绑定或持有证明提高凭据复制成本，但不保证受控设备不能充当代理；限流不能完全阻止慢速提取或转售。

## 强制给出批判性结论与处理方案

对用户方案采用“可采纳 / 需条件 / 不足以达到目标”结论，不为了顺从用户而认可安全承诺。每条高优先级问题包含：

- 证据位置或明确假设，以及攻击者需要控制什么；
- 哪个信任边界失效、影响哪项业务能力；
- 最小修复与推荐长期改造，涉及哪些模块/接口/状态；
- 验收动作及预期服务端行为、成本与合法用户影响；
- 修复后仍无法保证什么。

有源码时定位真实符号和数据流；无源码时提供标明假设的接口、字段、状态机、伪代码或配置模板，不虚构实现位置。给出分阶段迁移、旧版与离线用户处理、监控和回滚条件。涉及安全修复的回滚不能静默恢复已禁授权或重新暴露秘密。

## 以本地失陷为前提验收

仅在自有或明确获授权的隔离环境执行。测试接缝只能证明服务端策略；正式产物能否被修改需要另行验证。

| 验收场景 | 必须记录的结果 |
| --- | --- |
| 测试客户端完全跳过本地授权判断，无有效凭据请求新任务 | 服务端拒绝且不执行付费计算；界面能打开不算失败 |
| 曾经合法激活，保存云端下发常数/明文后撤销 | 观察旧数据是否仍足以独立完成新业务；能完成就否定“撤销后不能运行”的承诺 |
| 重放旧请求/结果，修改任务输入、租户、对象或功能等级 | 权限、任务归属和业务绑定有效；幂等重试按已定义语义返回原任务，不能误当作全新计算 |
| 无凭据、错误产品、已撤销凭据、低权限与其他租户凭据直接调用 API | 分别按服务端策略拒绝；不依赖官方客户端 headers 或隐藏 URL |
| 有效用户并发请求、排队后撤销、超时重试 | 执行时授权、配额、撤销窗口和扣费一致；记录最大生效延迟 |
| 断网或后端故障 | 未授权云计算不自动回退为本地放行；本地非受限功能及用户数据恢复按产品约定处理 |

依据：服务端逐请求授权原则见 [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)；客户端强制执行服务端安全策略的缺陷见 [MITRE CWE-602](https://cwe.mitre.org/data/definitions/602.html)。本文件的具体拆分方案仍需项目证据和实测支持。
